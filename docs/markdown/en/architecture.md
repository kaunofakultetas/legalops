# Architecture

The Compliance AI Assistant helps a compliance officer or LegalOps student establish which Lithuanian and EU acts apply to a financial-sector company. It extracts the concrete obligations those acts impose, compares them with what the company has, and writes the gap report. From the same documents it drafts the documents of a compliance programme — the compliance policy, the governance structure with the compliance process and its RACI matrix, the legal risk register — for a person to edit and approve. The user works in a chat; structured pages exist for review and administration. This document describes the system as built; [api.md](api.md) lists every route.

## 1. Services

| Container | Technology | Owns |
|---|---|---|
| `legalops-endpoint` | Caddy 2 | The only ingress: `/api/assistant/*` goes to the assistant, `/api/*` to Django, `/dbgate/*` to the database tool (administrators only), everything else to the GUI. It refuses a request whose `Origin` is another site's and sends a Content-Security-Policy and HSTS with every other answer (deployment.md §5). |
| `legalops-exit` | caddy-l4 | The only egress: an SNI allowlist (`ai.knf.vu.lt`, `publications.europa.eu`, `www.e-tar.lt`, `www.lb.lt`). Containers reach these hosts through `extra_hosts` pins. |
| `legalops-vite` | React 19, MUI 7, Tailwind 4, assistant-ui, TanStack Query | The GUI, a static build in production: two applications in one Vite project — the public site at the root of the origin (plain React and Tailwind, no session) and the console under `/console` (vite/README.md). |
| `legalops-django` | Django 5.2 (gunicorn), JSON only | Accounts and sessions, companies, documents, corpus, obligations, reports, prompts, chat history, usage, audit. The public API and the `/internal/assistant/*` door. |
| `legalops-worker` | Docker CLI | The job queue: it starts `manage.py run_worker` inside `legalops-django` with `docker exec`. |
| `legalops-assistant` | Node 24, Express 5, AI SDK 7 | Every model call. |
| `legalops-postgres` | PostgreSQL 17 + pgvector | All data, the vector indexes (HNSW, cosine) and full-text indexes (GIN, `simple`). |
| `legalops-dbgate` | DbGate 7 | No data of its own: a web client for the database, for administrators, served at `/dbgate/` — reached only through the endpoint, after Django's admin gate (§11). |

Design rules:

- **The assistant owns no data.** Prompts, threads, telemetry and MCP configurations live in Django. The assistant reads them through `/internal/*` with a shared secret, compared in constant time and failing closed.
- **Django never calls a model provider.** The worker and the web process ask the assistant for generations (`/internal/llm/generate`, strict JSON schemas) and embeddings (`/internal/llm/embed`). A generation is read from the provider as a stream and answered whole: a slow model writes the obligations of a dense batch for five minutes and more, and Node drops a response whose first byte takes longer than five. One call may take 15 minutes (`GENERATE_TIMEOUT_MS`); Django waits 930 s for it. Providers (`gateway:` — the university gateway, language models on its OpenAI Responses API, `openai:`, `anthropic:`, `ollama:`) are therefore configured once, in node. Model ids are `provider:model` strings stored on each prompt version.
- **Chat tools act through the public API with the user's bearer token.** The tenancy rule (a user sees their own rows; an admin sees all rows except other users' chat threads) is enforced once, in Django's views.
- **Every model call is an `LlmCall` row** with tokens, a USD cost from the gateway's price list, the prompt version and the outcome. Chat turns also carry the transcript. The one exception: the query embedding of a corpus or document search is not recorded (a few tokens per search).

## 2. Request flows

### Chat

1. The GUI sends `POST /api/assistant/chat` with the bearer token and only the new message.
2. The assistant resolves the user (`GET /api/auth/me`, cached for 15 s), applies the turn limit (12 turns per user a minute) and checks the daily USD budget (a failed check lets the turn through).
3. It loads the active `chat.assistant` prompt, the thread (with its company and adopted role), the company's compliance reports (ids, states, counts by status) and the thread history from Django.
4. It streams `streamText` with tools:
   - **Company:** profile, credentials, documents, roles.
   - **Corpus:** search, exact provision, citation check, act list, the obligations extracted from an act.
   - **Analysis:** cost estimate, run, stop, the list of reports, one report (counts whole and per act, findings by page and filter, action plan, citation audit), reviewer override.
   - **Programme:** start a work product (after the user's yes — it costs about half a dollar and takes minutes), and read one: the list of a company's products, or one product rebuilt small — a provision as one line, a quote as its document's title, the structure as an outline, the RACI matrix as one line a step — with the rules it breaks in words. The chat cannot edit or approve a product.
   - **Register:** read a company's action register and the changes in the law under its latest report. The chat cannot open, close or edit an action.
   - **External:** tools of the enabled MCP servers.

   The model is never left to ask the user for an id, a link or a page address the platform knows: the company context carries the ids of the company's documents, credentials, roles and reports, and a list tool finds every other. (2026-11-10: asked "how compliant is our company", the assistant requested the report's id twice — it had a tool to read a report and none to find one.)

   The assistant keeps the company's records without being asked (rule 1 of the prompt's tools since 2026-11-17, version 17 of `chat.assistant` once `seed_prompts` has run): whatever the user states or their documents establish is filed in the same turn, before the answer — the profile with every field the facts settle and its classification, each uploaded document with its kind, licences and certificates as claimed credentials, adopted standards, and a role profile for every management, officer or control position the documents define. A field that follows from the facts without being stated is filled with its reason under `attributes.inferred`; what nothing settles stays empty, and the answer asks for it. (Before, the assistant filed what the user stated and saved a role only when asked for one; on 2026-11-17 an upload of 26 documents left the roles empty and its answer was cut at the three-minute limit of a turn. A turn may now run fifteen minutes and 24 model steps; with those 26 documents it takes about six and a half minutes and costs about $2.60.) Since 2026-11-20 the same turn starts by itself when documents are uploaded on a company's Documents tab: once a batch is through, the console opens a conversation of the company and sends the turn in the user's name, with the documents attached (`pages/Companies/useDocumentIntake.js`; at most 29 documents a turn, later batches wait for a conversation of their own), and a notice on the tab links to it. Measured that day with the 26 documents uploaded to a company that held only its name: 278 seconds, five steps, the profile, the documents' kinds, one claimed licence and 20 role profiles filed, $2.89.

   A licence or certificate the user or a document mentions is recorded as claimed, with its issuer and number when given; the model sets "verified" only when the user says in so many words that the credential was checked. Verifying is the user's decision, stamped with their name. The prompt and the descriptions of the two credential tools say so since 2026-11-16 (version 16 of `chat.assistant` once `seed_prompts` has run); the code does not check that the user said it, as it does not for a finding's override. (Before, the tools invited the model to mark a credential verified once its issuer and number were known.)
5. When the turn ends, the assistant persists its reply through the internal door. It is the only writer of assistant messages, so a browser can never forge a tool output. It also logs the turn with its transcript and its tokens: every step's added up, and the part of the input the provider read from its prompt cache or wrote to it counted apart (section 7).

The assistant answers in the language the user writes in — the interface's language only when a message does not tell its own (the prompt's `{LEADING_LANGUAGE}`). (2026-11-10: asked in English in a Lithuanian interface, it answered in Lithuanian.)

### Report

1. `POST /api/reports` enqueues `report.analyze`.
2. The worker runs the steps in section 3 — in two parts when the report was started with the review: it stops in `scope_review` once it has decided which acts apply, and goes on when a person has approved the list (`POST /api/reports/{id}/scope`).
3. The GUI polls `GET /api/reports/{id}`. The finished report exports to PDF (WeasyPrint, `analysis/pdf.py`) and Excel (openpyxl, `analysis/exports.py`).

The PDF is the document handed to a board, so it reads from the conclusion down: a cover; the contents, down to the numbered sub-headings of the acts, the findings (one per act) and the methodology; the result at a glance (the counts, the open gaps by severity, a row per act); the executive summary; the action plan; then the material behind them — the company profile the report ran on, the acts and why each applies, the findings, the citation audit — and the methodology with what each status means and the provenance. Within an act the gaps come first, the gravest first, each as a card with the obligation, the assessment, the recommendation and the quoted evidence; obligations that could not be evidenced follow; those met are a compact table, and those that do not apply are only counted (the workbook lists every finding). The result is what binds the company today: the acts assessed as preparation follow with their own counts, never added to it, and the acts the report did not assess are listed with the reason — and, where their applicability waits for facts, with the questions to answer. Every page but the cover says where the reader is: above a hairline the company with its legal form and the section — in the findings also the act, and every act after the first starts a page, so the act in the margin is the act of the whole page; below one the mark, the product, the date and the page number. A finding's card names its act before the provision. It is set in the interface's faces, Source Serif 4 and Source Sans 3, which ship beside the module (`analysis/fonts/`, with their licences and how the files were made).

### Work product

1. `POST /api/companies/{id}/programme {kind}` enqueues `programme.generate` for a new version of that kind (the chat's `startWorkProduct` does the same).
2. The worker reads the company as a report does, asks the model in two calls, and puts the answer through the rules of the kind (section 3, "Work products").
3. The product comes out a draft. The GUI polls `GET /api/programme/{id}`; a person edits it (`PUT …/content`, through the same rules), approves it (`PATCH`), and exports it — PDF for every kind, Word for the policy, Excel for the risk register (`programme/exports.py`).

### Corpus refresh

1. `POST /api/corpus/documents/{id}/refresh` enqueues `corpus.ingest`. The scheduler also runs `corpus.refresh_all` weekly.
2. The worker fetches the source, stops early if it is unchanged, and parses the publication's markup in a resource-limited child process.
3. It writes the provision tree, chunks it per article, embeds, and activates the new version atomically. A version is made only of a text that changed: when the source issues the edition in force once more under another label — the register did so for the Law on Banks on 2026-11-15 — the text read equals the current version's, and the run ends as unchanged, the current version taking the new label.

## 3. The analysis pipeline

Obligations are **corpus-level**. An act version's obligations are extracted once (prompt `corpus.extract_obligations`) and reviewed by an admin (proposed → approved or rejected). Every later report reuses them. A second model orders that review (`corpus/verify.py`, prompt `corpus.verify_obligations`, queued per act by an admin or by `manage.py verify_obligations`): it compares each obligation with the whole article around the provisions it cites and keeps a verdict on it — supported, partly (who owes it, when or under what condition is not as written) or unsupported — with a note a reviewer can act on. The obligations page shows the doubted first; the judge approves nothing, and an obligation whose text is edited loses its verdict. (Measured 2026-11-12 on the 137 obligations of two laws: $0.19, and three doubts, each worth a person's eye — two duties cited to the article that only lists them, one condition the sentence leaves open. A first wording of the prompt doubted seventeen: it took a condition on a permission and the stated aims of the internal audit service for something less than duties.) A standard's requirements go the same way with their own prompt (`corpus.extract_requirements`); they are obligations of source `standard` that apply to everyone who adopted it, and the approved ones move to a new edition like an act's when their clauses kept path and text.

A new version of an act inherits the approved obligations whose cited provisions kept the same path and text, so a consolidation that changed three articles costs a review of three articles. Extraction inside a report run is shared cost and is charged to nobody; an extraction an admin queues from the corpus page is logged against that admin.

A provision that only lists infringements or sanctions is skipped: it repeats duties the articles impose (before the prompt said so, MiCA's Annexes V and VI added 134 repeats to its 393 obligations). An act is *behind* when it was never read, or was read before the prompt version now in force was written. After the extraction prompt or its model changes, `manage.py extract_obligations` queues every enabled act that is behind (operations.md §6): reviewed obligations stay, and an act keeps its present proposals until its new extraction has succeeded as a whole.

A report is made in two parts with a person's decision between them. The first — steps 1 to 4 — decides which acts apply and is cheap; the second judges every obligation of those acts and is where the money goes. A report started with `scope.review` stops between them in `scope_review`: the person sees every act with what the report would do with it and why, may take an act in (one waiting for facts, a directive, or an act that does not bind the company — assessed then by the company's choice, as good practice, with all of its obligations and counted like an adopted standard) or leave one out, is shown the price of the selection, and approves. The approval is stamped on the report (`scope_approved_by`, `scope_approved_at`), audited with every change, and the job is queued a second time — a new job of the same kind, which the report then points at; the stamp tells the second part from the first. The verdict stays on the act's row, so the report shows where a person decided against it. Without the review the run stamps itself — a time and nobody — and goes on; the exports say which it was. The second part reads the acts and the citation audit from their rows and the documents' inventories from their cache. The company it reads again, as it is when the scope is approved — profile, credentials, standards, documents: a credential verified or a document added while the report waited counts — and it freezes the profile a second time (`freeze_profile`), so that `profile_snapshot`, which the PDF's "Company profile" section and the report's page show, is the company the findings were judged on, not the company of the day the report was started. The cost of both parts is the report's (the jobs filed under it).

`report.analyze` steps (each a `JobStep` recording its prompt version, model, usage and duration):

1. **profile.** Freezes the company as it is into `profile_snapshot` — its adopted standards too. A report that waited for its scope is frozen again when its second part starts, without a step of its own (above).
2. **documents.** Indexes company documents not yet indexed. It then builds each document's evidence inventory (prompt `report.inventory`), cached per document hash, prompt version and inventory shape (`SCHEMA_VERSION` in `companies/inventory.py` — a changed shape re-reads every inventory once, even under an admin's own prompt version): controls with verbatim quotes, roles, registers, approval, review cycle, laws referenced, weaknesses, and `citations` — each reference to a specific provision as the document writes it (act, article, paragraph, point), with what the document claims it covers and a quote. (Until 2026-11-16 the prompt reached the model with the literal `{COMPANY_NAME}` in its first sentence: the call passed the language alone. The inventories made before stay as they are — the cache key holds no variable.)
3. **citations** — the citation audit. Every such reference is checked with `check_citations` (section 4): does the act's current version hold the provision, and does it regulate what the document claims (the citation judge, a model — gpt-6.1-sol by default; word overlap when it is unavailable, and each row records which judged). A reference several documents make word for word is judged once and fanned out; a range or list of articles is looked up article by article and answered by its best article; ≤ 50 lookups per judge call, filed under the step (the report's cost counts them). The judge weighs the subject a claim attributes to the provision: extra details of the document's own do not make a mismatch, and a claim that only says how the document uses the provision is "unclear". Rows in `report_citations`, problems first; counts in `stats.citations`.
4. **applicability.**
   - A catalogue screen first: the act's `applies_to` institution types and domain tags against the company's type and flags. An **unknown** flag keeps its domain in. The list is written by hand and ages with its act, so before an act is left out on its word the act's own scope provisions are read — once per version, prompt `corpus.scope`, the answer kept on the version (`corpus/scope.py`) — and the act is left out only when the list and the reading agree; an act the reading brings back gets the full verdict below. (The Law on Financial Institutions has counted crypto-asset services among financial services since 2024; its list never learned of it, and the report of 2026-11-11 left the law out for a crypto-asset service provider. Read on 2026-11-12, the scope provisions of the 51 enabled acts added institution types to five lists.)
   - Then the model reads each candidate act's scope provisions and answers applies / not_applies / uncertain with confidence (how sure the verdict would stand once every fact is known; for "uncertain", how likely the act is to apply after all), reasoning, citations, what is still to confirm — for "uncertain", the questions the company can answer about itself — `appliesFrom`, the date the act starts to bind the company when that is still ahead, and `effect`: "direct" when the act lays duties on the company, "institutional" when it organises an authority or a procedure before it (prompt `report.applicability`).
   - The verdict decides what the report does with the act (`report_acts.assessment`). An act that applies is **assessed**. One that applies from a later date is assessed as **upcoming**: preparation, counted apart from today's result. One whose applicability is uncertain is **unconfirmed** and not assessed — the report lists it with its questions, and a later run assesses it once the profile answers them. A directive is **indirect**: it binds through the national law that transposes it, which is assessed in its place. So is an institutional act — the law on the central bank, the regulation establishing an authority, a rulebook on fines, a licensing procedure: it reaches the company through that authority's decisions, and a company's documents have nothing to say on it. (In the report of 2026-11-11 five such acts made 42 findings, among them "recognise the independence of the Authority's chair — not evidenced".) An act the report's scope names is assessed through doubt — an uncertain verdict, an indirect treatment — but not against a negative screen or a verdict that it does not apply; such an act a person may take in at the scope review, as good practice. (Measured on the 1009 LTD report of 2026-11-10, which assessed every applicable and uncertain act alike: seven uncertain acts made 872 of its 2 120 findings, 823 of them "not applicable" or "not evidenced"; two directives were assessed beside the laws that transpose them; and the gaps under the AML regulation, which applies from 2027-07-10, stood among today's.)
   - Standards are never candidates. A standard applies because the company adopted it (`company_standards`: certified, implementing or planned — a planned one shows the gap still to close), or because the report's scope names it; it gets an "applies" row with `doc_type` standard and the adoption as its reasoning, without a model call. A standard not ingested yet is skipped.
5. **obligations.** Extracts the obligations of the acts to assess, and the requirements of the assessed standards, whose current version was never extracted. Keeps the non-rejected ones whose `applies_to` fits the company. The gap analysis reads a standard's batch under STANDARD rather than ACT, and the profile lists the adopted standards with their scope and certificate. The sanction provisions of the acts assessed are read in this step too, when nobody read them yet (below, "What a finding means").
6. **gap_analysis** (prompt `report.gap_analysis`).
   - Batches of 15 obligations (`OBLIGATIONS_PER_CALL`). Every call carries the company's documents **whole** — the same block in every call (`document_pack`), after the compact profile and before the act — so the model can tell "no document covers this" from "the passage was not retrieved", and can see a document refer to another that was not provided. The provider caches a prompt's repeated opening and bills what it reads from that cache at a twentieth of the input price, so the first call runs alone to fill it and the others, four at a time, read it. A set of documents over 600 000 characters (`DOCUMENT_PACK_CHARS`) falls back to the documents nearest to each batch's obligations (`nearest_documents`: by the better of an obligation's Lithuanian and English vectors, whole while they fit, a longer one in its nearest passages and marked as excerpts). Until 2026-11-10 every obligation was sent its six nearest passages: asked to check five "critical" findings of that day's report, the chat assistant read the documents themselves and found three of them wrong.
   - What can prove an obligation depends on what it asks for, and the prompt has the model decide that first: an arrangement that must exist, or conduct in the ordinary course of business, is proved by a document that establishes it; a fact about the company itself (where it is managed from, who its directors are, a licence, a filing) by the profile, a credential or a record — a policy neither proves nor disproves a fact, so an undocumented fact is "unknown", never "missing"; a prohibition by documents that forbid the conduct.
   - Each finding gets a status (met / partial / missing / unknown = not evidenced / not_applicable), an analysis, a recommendation and verbatim evidence quoted from the documents in their own language. The statuses: the report judges the company's DOCUMENTED arrangements (design) — "met" when the documents establish every element, with a short "verify in practice" note where operating proof matters, never a downgrade for it; "partial" names the missing element — one that changes what the company does, not the law's wording left unrepeated; "missing" only when the document dedicated to the subject is silent; "unknown" when no provided document deals with the subject, when a provided one refers to another that was not provided, or when nothing states a fact the obligation asks for; "not_applicable" for duties addressed to others or resting on a structure or step the company does not have — never for what the ordinary course of business brings (a request by an authority, an incident, a complaint). A claimed licence meets "hold a licence" with a caveat to verify it.
   - **A finding's severity is the obligation's own** — its weight in the register, the same in every report — so severity says how much the obligation matters and status how far the company is from it. (The model used to rate each gap: in the 2026-11-10 report 23 of the 42 "critical" open findings were reporting duties, four of them on obligations the register rates "low".)
   - **Every quote is placed.** The evidence a finding quotes from a document is located in that document's text (`locate_quote`: the model's quotation marks and line breaks aside) and stored with the place it starts at, which the GUI opens the document at. A quote the document does not hold word for word keeps its document and gets no place — the GUI says so under it. The step's output counts both (`quotesPlaced`, `quotesUnplaced`). The analysis and the recommendation name a document by its title; the refs of the prompt (`D4`, `C1`) stay in the evidence list. Reports made before 2026-11-10 stored a passage as a chunk of the document's index, and some carry refs in their texts; the PDF leaves the bracketed ones out.
   - Evaluated on 73 hand-checked findings of the demo report (2026-09-28): the previous prompt and retrieval were right on 71% of them and reported 21 problems the documents do not have; the passage-based ones that followed on 93%, with the same model (gpt-5.6-terra — gpt-5.6-sol scored 95% at twice the cost).
7. **action_plan** (prompt `report.action_plan`). Every open finding is planned. The findings go to the model by theme — the obligation's category — whole themes packed together up to 150 findings a call (`plan_parts`), each call told to close every finding it is given with exactly one action and to write at most eight; a finding a call still left out joins the action of that call nearest to it — one that closes a finding of the same act and theme, else of the same theme, else any action the call drafted, and among those the one that closes the most — so that no open finding is left without an action unless its call drafted none; the step's output counts the findings added this way and those left without one. Two more calls when there is something for them: the audit's wrong and non-existent references become corrective actions, and the acts that wait for facts become the action of finding those facts out. When the findings took more than one call, the drafts — each written without sight of the others, so that three amend the same policy and four ask the same officer for evidence — are merged into one plan (prompt `report.plan_merge`): every draft goes into exactly one action, which then closes what its drafts closed (measured on the reports of 2026-11-11: 48 drafts became 20 actions, all 645 findings kept; told to keep different documents and different subjects of evidence apart, 44 drafts became 24, the largest closing 65 findings where one had closed 123). The model sets each action's owner (the company's roles when defined), effort and timeframe; the order of the whole plan is the pipeline's — today's gaps before preparation for acts not yet in force, then the gravest obligation, a gap before a lack of evidence, the sooner timeframe, the more findings. (The plan used to be one call over the 160 gravest findings: on the 2026-11-10 report it left 806 of 966 open findings without an action.)
8. **summary** (prompt `report.summary`). The board summary with its limitations section and the report's title (printed on the PDF's cover). It is told what the report assessed and what it did not: the acts in force with their finding counts — in all and act by act, so it can say where the documents are strong and name an act most of whose duties nothing provided shows — and their gravest open findings (each with its act and provision; one where the company's own rules allow what the act forbids goes first), the acts assessed as preparation with counts of their own, the acts waiting for facts and the directives behind national law, then the plan's first actions and the audit's counts. It calls the statuses what the report calls them — "not evidenced" is not "unclear".

`stats.findings` and `stats.openBySeverity` count the acts in force, by effective status; `stats.upcoming` holds the same two for the acts assessed as preparation, when the report has any; `stats.acts` counts the acts by verdict and by what the report did with them. A review recounts them.

The report stores `stats.provenance`: every prompt version and model used, the version and date of every act read, and how many findings rest on person-approved obligations. Every title and text is snapshotted, so a report reads the same after the corpus or the profile changes. Reviewers override finding statuses with a note; the override wins in the GUI and the exports, and is audited.

A report whose worker died past its attempts fails instead of hanging. A job a deploy cuts off goes back to the queue once its heartbeat is two minutes old; a worker loop asked to stop hands its job back at its next checkpoint.

### What a finding means

The course's lecture on monitoring gives a finding four parts — the condition, the criterion, the cause and the consequence — and a report three questions to answer: what, so what, now what. A finding had the condition (the assessment and its status) and the criterion (the obligation and the provision behind it), and the action plan answered "now what". Three additions close the rest.

**Consequence — what a breach can cost.** The act itself says it: its sanction provisions set which infringements carry which ceiling and which measures. They are read once per act version (`corpus/sanctions.py`, prompt `corpus.sanctions`, one call an act over the articles whose heading speaks of sanctions, fines or measures) into **tiers** kept on the version (`legal_document_versions.sanctions`): the provision a tier stands in, the articles it covers — from a first to a last article, each by its whole number: 47-7, inserted after Article 47, and 45a are articles of their own — or "any infringement", the kind of breach it is bound to (systematic, gross, information not provided), whom it addresses, the ceiling of the fine — euros, a share of turnover, a multiple of the benefit, whichever the text states — and the measures beside it (withdrawal of the authorisation, restriction of an activity, a public statement, a ban on managers). Nothing is filled in from memory: a ceiling the text does not state stays empty. A report reads the acts it assesses in its `obligations` step; `manage.py read_sanctions` reads the rest of the corpus (operations.md §6).

A finding is then given its consequence **by code**, with no model call of its own (`Consequences.of`, stored on the finding as `consequence`): the tier that names the article of its provision before one for any infringement, one for whoever breaches the act before one that binds only certain persons, a company's and never a natural person's — and what that tier leaves unstated is taken from the other unconditional tiers of the same provision, because a provision often gives the sum, the share of turnover and the multiple of the benefit in separate points and a reading keeps them as one tier or as several; then a higher ceiling the act binds to a kind of breach or, beside a ceiling for everyone, to certain persons, shown with that condition and those persons; the measures of every tier that covers the provision merged in. A technical standard (a level 2 act of MiCA or DORA) lays down no sanction of its own: the catalogue names the articles of the parent act each was adopted under (`adopted_under` in `corpus/catalog.yaml`), and a finding under the standard is given what those articles cost, the entries carrying `via` — the parent act and the articles — which every wording ends with ("this act was adopted under MiCA 71 str."); a standard adopted under several articles that do not cost the same gets none. A tier may bind only some of the persons its act regulates (issuers of significant tokens, financial institutions as distinct from other obliged entities, cash handlers in a law about a central bank, essential entities beside important ones): the reading says whom (`persons`) — on a tier that names no article, and on one that names articles when the same provision sets another ceiling for another kind of person for them — the wording of the consequence repeats it ("only for: …"), and where a tier names no article and the register addresses obligations to those persons in the tier's own part of the act and nowhere else, the tier is narrowed to those articles (`_narrow`). An article that lists the infringements a sanction article refers to ("the infringements referred to in Article 29") is read with it, so the tiers name what the list names; a list that stands in another act is not read, and such a tier names the article that holds it and reaches no finding. A tier that is a periodic penalty and nothing else covers any infringement: the article named with it ("the instructions given under Article 33") is the one its order was given under, not one that was breached. A tier may concern another act — a national law lays down the fines for an EU regulation that leaves them to the Member States — and such a tier is taken only from an act the report assesses for this company. (Read on 2026-11-12, six sector laws each set fines for breaches of the DORA regulation — for banks, payment institutions, e-money institutions, credit unions, crypto-asset providers; a crypto provider's finding must show the crypto-markets law's ceiling, not the banking law's.) The PDF card, the Excel sheet, the console and the summary word it the same way and as what it is: the ceiling the act provides, not a forecast — shown for a gap, never for what is met.

Measured on the copy of the database, 2026-11-12: the 51 enabled acts read by the job in one run, 274 tiers, $0.65; checked against the texts for the crypto-markets law (Article 15), the anti-money-laundering law (Article 39), MiCA (Article 111) and the GDPR (Article 83); 882 of the demo report's 1,178 findings get a consequence — a finding under MiCA Article 68 "up to EUR 5 000 000 or 5 % of turnover" from the regulation and "up to EUR 5 000 000 or 10 % of annual income" from the national law, one under the transfer-of-funds regulation the ceilings of the anti-money-laundering law that its Article 36-1 carries over. The rule for technical standards, tried on the report of 2026-11-13 on 2026-11-16: 315 of its 332 gaps under level 2 acts get a consequence; the 17 without are under the standard on sustainability indicators (MiCA RTS 2025/422), adopted under four articles that do not cost the same. A report made before keeps what it stored.

**Cause — why the gap exists.** A field of the finding (`cause`) that only a person writes, in the review dialog. Documents show that something is missing, never why — a procedure that was not updated after a law changed, an owner who was never appointed — so the model is not asked and the chat does not file one.

**The company's own rules as criteria.** A report started with the `internal` option also judges whether the company does what it told itself to do (`analysis/internal.py`, step `internal` after the gap analysis). The requirements are read out of its policy-level documents — levels 1 and 2 of its compliance policy's document hierarchy when it has that work product, the documents filed as policies otherwise — one document a call (prompt `company.internal_requirements`), each requirement with the passage that states it, placed in the document; they are kept as obligations of the kind "internal" and read again only when a document's file (its SHA-256) or the prompt version changes. Each is then judged against the whole library (prompt `report.internal_gap`, the gap analysis's answer shape) with one rule the legal check does not have: **the policy that states a requirement is the criterion and never the evidence** — what counts is another document that carries it out. The findings hang on an act row of their own (`doc_type` "internal"), are counted apart (`stats.internal`) and worded as gaps between the company's policies and its procedures, not breaches of law; their open ones go into the action plan with the rest. The step stands beside the report's main path and changes nothing in it.

### Over time: the action register

A report's plan used to die with the report: the next analysis wrote a new one, and nobody could say what became of the old. The register keeps it (`analysis/register.py`, table `company_actions`). It moves on **one event only — a person signing a finished report off**, or taking that signature back:

- **The actions there are get held against the signed-off reports.** A finding under an action is confirmed when the reports made since the action's own find its obligation met; an action whose findings are all confirmed is closed by the report that completed them. An obligation a report did not assess confirms nothing. One that a report made after the owner called the action done still finds open sends it back to work — the course's rule that a finding is closed only after a re-test, with the next signed-off report as the re-test. A report made before the action was called done sends nothing back: it never saw the finished work.
- **The reports speak in the order they were made, not the order they were signed.** The confirmations are worked out from all the signed-off reports each time (`_settle`), so an old report signed late does not overrule a newer one, and the register comes out the same whatever the order of the signatures.
- **The report's own plan comes in:** each action with the open findings it is to close, the plan's owner role and a due date counted from the sign-off (a fortnight, 30 days, 90 days, a year). An obligation already under an action that is not closed gets no second one; a sign-off withdrawn and given again brings nothing twice. An action that closes no finding — correcting the documents' references, finding out a fact — comes in too and only a person closes it; the next report's action of the same kind is not added while it is live.

An action is `open`, `in_progress`, `done` (the owner's word, awaiting the re-test) or `closed`; **late is not a state but an open action past its due date**, derived when the register is read. A person owns, dates and moves an action (`PATCH /api/actions/{id}`) and may close one by hand only with a note that says why; the register records whether a report or a person closed it. A closure by hand is the person's to take back; what a report closed is not reopened by hand — its closure rests on that report's findings and is disputed there, at the finding.

**A closed action stays closed, and a closure falls only with the evidence under it.** When a later report finds the obligation open again, that report's plan brings a new action and the summary counts the gap as one that went back. Withdrawing a sign-off — by hand, because a reviewer changed a finding afterwards, or because the signed-off report is deleted — takes back what that report alone confirmed: a finding another signed-off report also finds met stays confirmed, and a closure that rested on the withdrawn report goes back to the state it was closed from.

An obligation is known by its id, and that id survives a re-reading of its act only once a person has approved the obligation: a finding whose obligation was replaced since confirms nothing, and its action stays for a person to close — the register says so on the action (`byHandOnly`). A requirement of the company's own keeps its id when its policy is read again and the passage that states it is unchanged (`analysis/internal.py`). This is why the review of the register of obligations comes before relying on the confirmations.

**History and movement.** A finding served with its report carries how the same obligation stood the last times an earlier finished report assessed it (`history`), and a report's stats what moved, obligation by obligation (`stats.changes`): gaps closed, new gaps, and obligations that were met and are a gap again; the summary says so in a sentence and the PDF in a line. Each obligation is held against the last earlier report that assessed it, not only the report just before — a report on a few documents or acts in between would otherwise make everything else look new.

**Changes in the law.** When a new version of an act is activated, what it changed against the one before is recorded article by article (`legal_document_versions.changes`: changed, added, removed — white space aside). For a company's latest report, `GET /api/companies/{id}/law-changes` lists the assessed acts that have a newer version, the provisions that changed, and the findings that rest on them — the ones to look at again.

Tried on the copy of the database, 2026-11-12, with the real reports there and no model call: signing the full demo report off brought its 25 plan actions in with the 587 open findings they are to close, every one with its obligation's id; signing the later small report off added 7 and left 6 out as already under way. Signed the other way round — the newer report first — the register held the same 653 findings, none under two actions. A re-test (the full report copied, some findings set to met) confirmed 7 findings, closed the action whose findings were all met and sent back to work the one called done that still had one open; withdrawing its sign-off undid exactly that, and deleting it after a second re-test left the closures standing on the second.

### Measuring the prompts

The test suites run against a fake model: they prove the plumbing, not the prompts. What a prompt does is measured by labelled cases kept in the repository (`django/compliance/prompts/evals/`): each case carries the answer a careful reader gives and the reason, and `manage.py eval_prompts` puts it to the real model through the function the product itself calls — `gap_data`, `applicability_data`, `check_citations`, the judge's and the scope reader's own renderers — so a suite measures the prompt as it is used. A run prints every case the model got wrong and fails below the committed baseline (operations.md §12).

| Suite | Cases | What a case is | Baseline 2026-11-12 (gpt-6.1-sol) |
|---|---|---|---|
| `gap` | 71 | An obligation and the status the sample company's 26 policies deserve for it; the whole library goes with every call, as in a report. Labelled by two readers who did not see the model's answers; where two careful readers could differ, the second status is accepted. | 67 (two may be lost to run-to-run variation) |
| `applicability` | 19 | A company profile and an act: applies, does not, or waits for a fact — and, where a report's treatment turns on it, the act's effect or the date it starts to bind. | 19 |

| `verify` | 14 | A provision and a register entry: supported, or to be doubted. | 14 |

### Work products of a compliance programme

A report says where the company stands against the law. The documents that make a compliance management system — the ones the course's second and third assignments ask for — are **work products** (app `programme`, table `work_products`): generated in the background from the company's documents, checked by code against the rules of their kind, edited and approved by a person. There are three kinds, each building on the ones before it — on the approved version, or on the latest draft when none is approved:

| Kind | What it holds | Rules that stop approval | Rules that only warn |
|---|---|---|---|
| `policy` | The compliance policy in the eight parts the course teaches (purpose and fit; management commitment; the function's mandate; commitment to requirements and improvement; roles by the three lines; core processes; whistleblowing; consequences), each with the documents it rests on, its legal basis and the points the governing body has yet to decide. Every document of the company on its level (1 policy, 2 thematic policy, 3 procedure, 0 not a rule). The missing level-2 and level-3 documents, each with its purpose, priority and legal basis. | All eight parts written; every article named exists in its act. | An act outside the corpus; a provision that does not regulate what it is named for; a quote the document does not hold; a document left without a level. |
| `governance` | The positions and units the documents name, the roles missing or unclear, a structure of bodies, committees, functions and units by line of defence (what the documents do not name is marked proposed), the compliance process in verb-named steps resting on ISO 37301 clauses and the Bank of Lithuania's guidelines, and the RACI matrix of steps against roles. | The structure is a tree under a governing body with no unit left unconnected (an outside party may stand beside it); the second line is not under the first and internal audit reports to a governing body alone; at least five steps; **every step has exactly one accountable role and at least one responsible** (a cell may be "AR"). | A role in every step; a role accountable for more than half; a step resting on an unknown clause; an unplaced quote. |
| `risks` | The likelihood and impact criteria — five levels by four dimensions each, the money thresholds scaled to the company and every assumption stated — the five bands of the 5×5 matrix with what each means and who decides, and the scenarios in the lecture's sentence ("A likely [event], arising from [source], may cause [consequences] that will affect [objective]"), each with its type of legal risk (ISO 31022 Annex A), unit, internal policies, legal basis, what the documents and the latest report show, its levels on the eight dimensions, response, actions, owners and deadline. | Complete criteria, with what each band means, who decides and how the scales were fitted; at least five scenarios over at least four of the six types; every scenario with the four parts of its sentence, a unit and a policy of the company, and all eight levels; every article named exists. | Acts outside the corpus; subject mismatches; no owner or deadline; a response the band does not allow; a sentence off the set form. |

How a product is made (`programme/run.py`, job `programme.generate`, one attempt):

1. **documents.** The company's profile and every document whole, as in the gap analysis — the same block in both model calls, so the second reads it from the provider's cache. A library over 600 000 characters fails the run saying so, rather than write a policy from excerpts. The latest finished report gives the open findings a missing document or a scenario's internal conclusion can rest on.
2. **Two model calls per kind** (prompts `programme.policy` and `programme.documents`; `programme.structure` and `programme.raci`; `programme.risk_criteria` and `programme.risk_scenarios`), the second given what the first wrote.
3. **references.** The kind's `validate` brings the answer into the kind's shape and checks its rules. Every quote is located in the document it names (`locate_quote`); every provision is looked up in the corpus with `check_citations` and — once, at generation — judged for whether it regulates what the text says of it. The checks are stored on the product (`checks`: rule, ok, detail, blocking).

**Numbers are computed, never taken from the model.** A scenario's likelihood is the mean of its four dimensions rounded half up, its impact the highest of its four, the score their product, the band read off the lecture's table (1–3 negligible, 4–6 tolerable, 8–12 medium, 15–16 high, 20–25 critical); scenario ids are numbered in order; the bands and their allowed responses are constants. The model gives the eight levels with a reason for each side, and is told to score the reasonably foreseeable serious case and say which case it scored. (The first register for the demo, 2026-11-12, gave nine of ten scenarios the same impact levels — "a fine, the licence not presumed lost" — and placed a doubt about the scope of the authorisation itself nowhere; told to weigh each scenario on its own facts and to put first what could cost the authorisation, client assets or a core service, the second spread them from 9 to 20. It then leaned on the financial policies alone, where the assignment ties scenarios to the technology, operations and security units and their policies; told that each of those units owns a scenario and that a third of the scenarios turn on the operational and information-security policies, the third did.)

**A person's edit goes through the same door.** `PUT /api/programme/{id}/content` takes the whole content, runs `validate` on it — without the model: lookups by text, levels and bands recomputed — and stores what comes out, so an edit can mend a broken rule or break one, and the page shows which at once. **Only a person approves**, only a draft, and only while no blocking rule is broken; approval freezes the product, and changing it afterwards is a new version copied from it (`POST …/revise`). The system approves nothing itself.

**One drawing.** The structure is drawn by the backend (`programme/chart.py`) as SVG for the page and the PDF alike: the upper levels as rows ordered by line — the three lines read left to right — the childless functions of a body hung together on a rail, the deeper levels stacked; how many levels spread as rows is whichever fits a landscape page best. In the PDF the chart, the RACI matrix (role names running up their columns) and the register (the lecture's nine columns) stand on landscape pages; the cover says whether a person approved the product, and the last section lists the rules as the product met or broke them and what it was made from.

Measured on the demo company, 2026-11-12, on a copy of the database (gpt-6.1-sol): the policy $0.46 and five minutes — eight parts, 23 of 23 quotes placed, 24 of 24 provisions found, 16 missing documents; the structure and RACI $0.39 — 46 positions, 15 gaps, 25 nodes, 14 steps, the golden rule kept, one warning (the compliance officer takes part in every step); the register $0.35 to $0.48 — ten scenarios over all six types of legal risk and six units, seven of the IT policies among the seventeen they concern, every rule kept.

## 4. The legal corpus

**Sources.** Two sources refuse unattended clients: EUR-Lex (a WAF challenge) and e-seimas (a Cloudflare JavaScript challenge). The same texts therefore come from their official machine interfaces:

| Source | How the text is fetched |
|---|---|
| CELLAR | SPARQL finds the newest consolidated version in force (future-dated consolidations are skipped); the XHTML is content-negotiated in Lithuanian. CELLAR's `303 http://` redirects are upgraded to https. |
| e-tar.lt | The edition valid today is picked from the editions table; the register's structured HTML is fetched. An unknown id answers 200 with a "not found" body, which is detected. |
| www.lb.lt | Pages and PDFs. |
| Plain HTTPS / upload | Plain HTTPS works only on allowlisted hosts; uploads are always accepted. |

The fetcher checks the scheme and the port of every address — https on port 443 only (a plain-http address is upgraded), checked again on every redirect hop — and paces itself to one request per second per host. Which hosts it can reach is not its decision: the container it runs in (`legalops-django`) resolves only the hosts its `extra_hosts` pin, and the exit passes only its allowlist.

**Level 2 and the supervisor's instructions.** Beside the primary acts the catalogue holds the texts that say how an obligation is carried out: the regulatory and implementing technical standards under MiCA and DORA that bind a provider's conduct (each has its own CELEX number and is fetched like any EU act), the Bank of Lithuania's instructions on money-laundering prevention and on international sanctions (e-tar), and the EBA's ML/TF risk factor guidelines. The EBA's site is not on the egress allowlist, so the catalogue only creates the rows of its two guidelines (source `upload`, with the address of the official PDF) and a person uploads the files on the act's page. The standards that bind only an applicant for authorisation, an entity notifying under MiCA Art. 60 or one picked for threat-led penetration testing ship disabled, like CRR and CRD — and so do the two DORA implementing standards that are a report form and a register template: read for obligations they give one for every field (68 for the incident-report form, measured 2026-11-12), which a report on a company's documents cannot use. A level 2 act is a candidate for the companies its parent act is a candidate for, and the report gives it a verdict of its own. A level 2 act has no sanction provisions — they stand in the parent act and name the parent's articles — so a finding under it carries the consequence of the article it was adopted under, which the catalogue names (above, "Consequence").

**Acts read from a PDF.** An act without a structural parser — a guideline published as a PDF — is read from its extracted text by the line parser (`corpus/structure.py`). What every page repeats (running titles, page numbers) is removed first, by the routine the standards reader uses (`corpus/standards.py` `without_furniture`). A supervisor's guidelines number their paragraphs "4.1.", "4.2." under headings that carry no number of their own ("4 gairė. …", "Guideline 4: …"): each heading opens a section and each paragraph is a point of its own, cited "4.2 p.". A guideline printed without its paragraph numbers (guideline 2 of the EBA's consolidated ML/TF risk factor guidelines, in the Lithuanian and the English PDF alike) keeps its text as one part, and extraction reads such a part whole. Measured on the copy, 2026-11-12: the consolidated guidelines give 20 sections and 372 points; the one act that was already read this way (the Bank of Lithuania's compliance function guidelines) keeps every unit and loses twelve stray page numbers.

**Structure.** Structural parsers (`corpus/sources/`) read the publication's own markup:

| Parser | Reads |
|---|---|
| `eu_xhtml` | Official Journal, consolidated and old flat consolidated XHTML |
| `etar_html` | e-tar consolidated HTML |
| `lb_html` | lb.lt pages |

Each prints a citation per unit ("59 str. 1 d. a p.", "Art. 59(1)(a)", "5.1 pap."). Other formats fall back to sandboxed text extraction plus the line-based structure parser. Units keep their full text, so an article row alone answers "quote Article 59".

**Standards.** A standard (`doc_type` standard — ISO, IEC, EN, ETSI or an LST edition, or a framework or control catalogue of any other publisher; usually jurisdiction `INTL`) is an uploaded copy. After the sandboxed text extraction, which keeps a standard's pages apart (form feeds), `corpus/outline.py` gives every readable copy a tree of citable units, by the first of three ways that works — recorded as the version's parser:

1. **The rules** (`standard`). `corpus/standards.py` reads numbered clauses and lettered annexes. A document they read is never sent to the model, except for a clause they leave longer than 15 000 characters: the model marks the headings inside it, and they become its subclauses when at least three carry an identifier of their own — the controls of a catalogue inside a numbered chapter (`standard-refined`).
2. **The model** (`standard-ai`), when the rules find no structure (fewer than three clauses, most of the text before the first one, or one clause holding more than half of the text): prompt `corpus.standard_outline` is shown the text as numbered lines, 28 000 characters a call, with the headings found so far, and answers which lines are headings — line, last line, level, identifier. The model only points: every heading, identifier and line of text in the tree is the document's own. A line outside the excerpt, an identifier the line does not open with (or that ends inside a word), a "heading" that reads as a paragraph are dropped; an identifier in brackets counts on from the numbered heading above it (enhancement `(1)` of `AC-2` is `AC-2(1)`); of several headings with one identifier those with next to no text go (entries of a summary table); the levels are counted anew from the nesting.
3. **The pages** (`standard-pages`), when neither works or the prompt or gateway is unavailable: each page is a unit cited by its number ("p. 12" / "12 psl."); a text that shows no pages is cut into parts.

Whatever the way, the own text of a unit still longer than 24 000 characters is cut by its pages ("Clause 5, p. 31"), so nothing is cited to forty pages at once; glossaries, informative annexes and the like are left whole. Only a file without text (a scanned copy, a locked PDF) is refused. The admin can have a standard read another way (`structure`: `auto`, `rules`, `ai`, `pages`) when it is processed again. A version processed again keeps its obligations on the units of the same citation; proposals whose units are gone are deleted, reviewed ones stay cited by path alone, and the version then counts as never extracted. The model's calls are shared corpus work, charged to nobody; measured on real documents (2026-11, gpt-5.6-terra): the 106 outcomes of the NIST Cybersecurity Framework 2.0 in one call, all 286 requirements of the OWASP ASVS 4.0.3 in six (about 0.25 USD, 90 seconds; a smaller model missed 16), the first 17 controls of NIST SP 800-53's access-control family with their 94 enhancements in four (the whole catalogue, 492 pages, takes about sixty calls). The 17 families and 130 requirements of NIST SP 800-171 are read by the rules.

The rules come from real copies (2026-11: ISO/IEC 27001, 27002 and 42001 as their publisher typesets them, ETSI EN 303 645, the 114-page ISO/IEC drafting directives, the Lithuanian LST guides, NIST SP 800-53 and 800-171, the EBA guidelines on ICT risk — `tests/test_standard_layouts.py` and `tests/test_standard_outline.py` keep their layouts):

- **Page furniture.** Each page is peeled from its top and bottom while the line there stands at about that distance from the edge on a quarter of the pages (digits and stray spaces ignored), is a lone page number, a copyright line, a rule drawn across the page or a first page's running title. A stamp of several lines under every page, a page number glued to the copyright line on one page and alone on the next, a page number printed first — all go; a term number alone on a line inside the page stays. The running head of one chapter or appendix ("APPENDIX A PAGE 394"), too rare for the whole document, goes where it is the outermost line on three pages in a row (five when it carries no number).
- **Contents.** Dot-leader lines go; an entry wrapped over two or three lines goes whole. Contents printed without leaders open clauses that take no text and are thrown away when the numbering starts over.
- **Clauses.** A line opens a clause only when it continues the numbering (a child, the next sibling, an ancestor's next sibling; two lost headings allowed, twenty among headed subclauses of one clause), so a sentence that starts with a number stays text. A number alone on its line takes the next line as its heading (term entries; never a lone integer, which is a page number or a table cell). A heading may wrap — in an annex's table columns over several lines, a word broken by a hyphen rejoined — and the column word of a control table ("Control") is dropped from it. A clause is numbered as printed (a requirement printed `03.01.02` is cited so, and found as `3.1.2` too); a heading whose first letter the PDF sets on a line of its own is put together.
- **Numbered lists.** "4. …" after "3. …" is a list item, not chapter 4: a whole number with a full stop that follows, within a dozen lines, the number before it — which itself opened nothing — goes on a list. Without this, the lists inside the controls of a catalogue read as its chapters.
- **Numbered paragraphs.** Where subclauses are numbered paragraphs (most Lithuanian guides, the conformity-assessment standards), each is a clause without a heading: a subclause number, a capital letter, and the sentence before it ended — which keeps a cross-reference that merely starts a line as text.
- **Annexes.** "Annex A (normative)", "Annex A (informative): Title", "A priedas (norminis)" with the title on the next lines. An annex cannot open before the body has (contents, foreword); one that starts a page is certain, one named mid-page is on trial and undone when the body's numbering goes on (a standard that shows an annex's heading as an example). A control table that leaves the annex letter out (ISO/IEC 27001:2022 Annex A, 5.1–8.34) is read as A.5.1–A.8.34.

Units are `clause` (path "Clause 4" / "4 skyrius" for a top-level clause, the bare number below, "A.5.15" in an annex; for a unit the model marked, its identifier as printed — "AC-2", "GV.OC-01", "V2.1" — or its heading when it has none; for a page, "p. 12") and `annex`; the front matter is a `preamble`, the bibliography a `text` unit. A PDF secured against copying opens with its empty password (AES needs the `cryptography` package of the image); one that needs a password or is locked by a rights-management plug-in fails with that reason. Chunks are leaf clauses opened by their ancestors' headings ("6 Planning › 6.1 …"), short sibling clauses grouped up to 2000 characters. References name a standard by its designation with or without publisher and year ("ISO 27001" → the latest edition; an international standard and its adoption answer for each other across their different years, "ISO/IEC 27001:2022" ↔ "LST EN ISO/IEC 27001:2023") and a clause the way texts cite it ("clause 6.1.2", "Annex A 5.15", "A.5.15"). A bare number the body lacks is looked for in the normative annexes, and a reference that says "control" means the annex's even when the body has that number (27001's 5.1 is leadership, its control 5.1 the policies). A reference that is a unit's citation as the corpus shows it names that unit; otherwise an identifier is matched as printed, then by its letters and digits alone ("ac 2 (1)" is AC-2(1)), a page by "p. 12", "page 12" or "12 psl.", and a number behind a letter the standard does not print ("V2.1.1") by the number. Requirements are extracted from the clauses without subclauses and from the own text (40 characters or more) a clause holds before its subclauses — a control and its enhancements are read apart — skipping the top-level units that state none (the numbered introduction, scope, references, terms, a glossary, a frontispiece…), informative annexes, the preamble and the bibliography.

**Retrieval.** Chunks are article-scoped (long articles split between paragraphs; recitals and points grouped). Each is embedded with its act, path and heading. Search is hybrid: cosine nearest neighbours plus Postgres full-text search, fused by reciprocal rank. It degrades to keyword-only search when the gateway is down.

**Embedding model.** `text-embedding-3-large`, asked for 1536 dimensions (the width of every vector column). Measured on 2026-09-28 against `-small`: an obligation's English text found its own article among the Lithuanian MiCA chunks 38 times in 40 (small: 23), DORA 33 (29), PPTFPĮ 37 (34); Lithuanian queries scored about the same (39/35/37 against 36/37/36); and the reports' company evidence — the right document among an obligation's six nearest passages — 38 of 41 (small: 35), with a mean reciprocal rank of 0.83 (0.79). The chat often searches in English and company documents are often English, so the cross-language gain is the one that counts; the cost is about $0.13 per million tokens, some $0.30 for re-embedding everything.

**Citations.** `find_provision` resolves exact units by short title, slug, id, CELEX or a unique title fragment — and, the way company documents name acts, by an EU act's type and number ("Regulation (EU) 2023/1113" → CELEX 32023R1113) or a short title the reference opens with ("MiCA Regulation", never "Guidelines under MiCA"). An inserted article is found under either spelling: the line parser stores it as `12¹`, the e-tar parser as `12-1` (cited "12-1 str."), and a lookup — here and in `check_citations` — asks for both (`number_spellings` in `corpus/structure.py`). It answers the verbatim text, the version and date, and a link to the official text (`citation_url` in `corpus/links.py`): EUR-Lex at the article's anchor `#art_N` for an EU act; otherwise the address the catalogue gives the act (lb.lt pages, PDFs), or — for an act from e-tar, whose catalogue entry gives an id and no address — the act's page in the register of legal acts, `https://www.e-tar.lt/portal/lt/legalAct/<id>/asr`, the consolidated edition in force. There is no anchor to an article on e-tar: that link opens the act.

`check_citations` verifies claimed article references. A model (prompt `corpus.check_citations`, gpt-6.1-sol; first measured on gpt-5.6-luna) compares the claim with the real heading and opening text by meaning, across LT and EN. It scored 12/12 on the MiCA 74/77–83 references the 1009 LTD sample gets wrong; embedding similarity scored no better than chance on the same set.

## 5. Data model

All tables use aware UTC timestamps and enum CHECK constraints in `Meta.constraints`. Their primary keys are uuid4 text minted in Python, except the two keyed by a natural key: `rate_limit_windows` (the limiter's key) and `model_prices` (the model id).

| App | Tables |

## 6. Security

**Authentication.**
- Opaque bearer tokens of 256 random bits, stored as sha256, with a 30-day expiry; an account keeps its 10 newest sessions.
- bcrypt passwords of at least 10 characters and at most 72 bytes (bcrypt's ceiling).
- Login is limited per IP and per account in Postgres and timing-equalised. The account window is keyed on the account the email resolves to, and the change-password check counts in it. Failed logins and failed password checks are audited.
- There is no self-registration; admins create accounts. The last active admin cannot be removed.

**Input handling.**
- Strict JSON: no NaN, Infinity or overflowed numbers (`1e999`), no NUL or lone surrogates, bounded nesting, typed and capped field readers, database-refused values mapped to 400.
- Uploads are sniffed (binary content named as text is refused) and extracted in a child process with memory and CPU limits and a wall-clock timeout.
- Exports fetch nothing — the PDF renderer may open the font files bundled with the code and no other address — and write no spreadsheet formulas.

**Prompt injection.**
- Company data and documents enter prompts as delimited data with an explicit "data, not instructions" rule.
- Tool outputs the model sees come only from the server-side history.

**Network.**
- Only the ingress is published. It forwards only `/api/…` paths to Django and the assistant, and both `/internal/*` doors also demand the shared secret. It answers 403 to a request whose `Origin` header names another site, and sends a Content-Security-Policy and `Strict-Transport-Security` with every other answer (deployment.md §5).
- `/dbgate/*` reaches the database tool only when Django's gate (`GET /api/auth/checkauth/admin`) answers that the caller is an active administrator; the tool itself sits on the isolated network (§11, "The admin database tool").
- Egress is an SNI allowlist.
- Corpus fetches go over https on port 443 only, checked again on every redirect hop: of the stack's own services only the exit listens there, and it passes nothing but its allowlist.
- MCP server URLs must be https to a public DNS name: the assistant connects from inside the isolated network, next to every service.

**Containers.** Read-only root filesystems everywhere. The endpoint, the exit, Django and Postgres run as uid 1000. The GUI and the assistant run as their image's default user, root: the compose file's `user: 1000:1000` line is commented out for both, and none of their Dockerfiles sets a `USER`. `legalops-worker` runs as root to use the Docker socket (no network, one fixed command), and `legalops-dbgate` as root too. No `init`, no capability drops, resource limits or healthchecks. See [deployment.md](deployment.md) §1.

The pre-release audit, its findings and the residual risks are in §11.

## 7. Cost control

The faculty gateway key carries a **team budget** ($10 when this was written). When it is used up, the gateway refuses every call with HTTP 402. The product then says so plainly (`AI_BUDGET_EXHAUSTED`) instead of failing generically, and a report failed that way keeps everything it had already paid for.

**Per-user budget.** Each user may spend `LLM_DAILY_BUDGET_USD` per UTC day (default $10), or an admin-set override (`dailyBudgetUsd`, where 0 means unlimited). Admins, the operators who set budgets, default to unlimited.
- The chat checks it before every turn, as do prompt test runs. A citation check with the budget spent is judged by word overlap instead of the model.
- A report needs $0.25 left to start; a started run is never stopped halfway.
- A work product needs $0.25 left to start and costs about $0.4–0.5; its calls are logged against the user who started it.
- Reading an act's sanction provisions is shared corpus work, charged to nobody (about a cent and a half an act). The requirements of a company's own policies and their assessment are charged to the user who started the report.
- Obligation extraction inside a report run is shared corpus work and is charged to nobody; an extraction an admin queues from the corpus page is logged against that admin. Corpus ingestion is charged to nobody.
- Document indexing (the embeddings of an upload) is charged to the uploader; once their daily budget is spent, the indexing job waits for the reset (it re-queues itself for 00:05 UTC) instead of embedding (§11, "Cost").

**Default model per step** (every prompt version can pick another in the prompt editor):

| Step | Model | Why |
|---|---|---|
| Chat | gpt-6-astra ($10 / $50 per M tokens) | The shipped default; an admin picks another in the prompt editor, and a default they only moved to another model keeps that model when its text is updated |
| Applicability, gap analysis, document inventory, action plan, summary | gpt-6.1-sol ($2 / $10) | The whole report on one model: it judged the demo's requests as gpt-6-astra did, at a fifth of the price |
| Obligation and requirement extraction, the structure of a standard, the scope of an act | gpt-6.1-sol ($2 / $10) | One-time corpus work every report reuses: the most thorough reader measured |
| Citation checks (the checker and every report's audit) | gpt-6.1-sol ($2 / $10) | Short comparisons, a few calls a report |
| The judge of the register | gpt-6.1-sol ($2 / $10) | One-time corpus work: $9.80 and 369 calls for the 5,960 obligations of the register (measured 2026-11-13) |
| Work products (policy and missing documents, structure and RACI, risk criteria and scenarios) | gpt-6.1-sol ($2 / $10) | Two calls a product over the whole library; the second reads it from the cache |

**Measured on the 1009 LTD demo** (26 policies; MiCA, DORA, TFR, GDPR, KRĮ and PPTFPĮ applicable):
- Document inventories: $1.09.
- One-time obligation extraction for the six acts: $4.98 for 700 obligations (on gpt-5.6-terra, the model of that day). Later reports of any company reuse it.
- The extraction model, measured 2026-11-10 on two batches (MiCA Art. 68–75, PPTFPĮ Art. 10–13): gpt-6.1-sol listed 56 and 32 obligations where gpt-5.6-terra listed 44 and 25 — among them duties terra had merged away or left out (the client's right to assets a ledger change creates, liability for lost client assets, the conditions a relied-on third party must meet). gpt-6-astra gave practically the same lists at five times the price. The GPT-6 models write about 70 tokens a second, half of terra's speed: a dense batch takes four to six minutes.
- Applicability: $0.33 on gpt-5.5; about $0.06 a call of four acts on gpt-6.1-sol (seven calls for the demo's 26 candidate acts).
- Gap analysis (measured before the cheaper defaults): about $0.23 per 10 obligations on gpt-5.5. The current defaults (15 per call, compact profile, concise findings) cut that several-fold: a call of fifteen obligations on gpt-6.1-sol reads 16–22 thousand tokens and writes 3–5 thousand, about $0.08.
- The report models, measured 2026-11-10 on the demo's real requests (three gap-analysis batches of fifteen obligations — MiCA, PPTFPĮ, DORA — and two applicability batches of four acts): gpt-6.1-sol and gpt-6-astra gave the same status for 43 of the 45 obligations and the same verdict for all eight acts; gpt-5.6-terra differed from them on five obligations, each time by overlooking a passage or by holding a policy to something the obligation does not ask. The GPT-6 models quote more of the passages they rely on and name the element that is missing more exactly. An action plan and a summary written by each from the same twenty open findings covered all twenty and read alike. gpt-6-astra costs five times gpt-6.1-sol for that — about $57 against $11 for the gap analysis of the demo's 2 200 obligations, and about $3 against $0.60 for the other steps — so every step of a report runs on gpt-6.1-sol.

**What the provider caches, and what a call costs.** Measured on gpt-6.1-sol on 2026-11-10/11: the provider caches a request's instructions and a request as a whole — a later request reads what it repeats word for word from the start (the same instructions; an earlier request it repeats or extends, as each step of a chat turn extends the one before), and nothing of a message that only begins alike. Input read from the cache costs a twentieth of the input price ($0.10 per M tokens); every other input token is billed as written to the cache, a quarter above the input price ($2.50). The same 8 800-token block sent twice was read from the cache when it stood in the instructions, and written anew as the opening of a user message whose end differed, as a message of its own before a different one, with a cache key and with a retention hint. Three things follow:
- A step whose calls share data sends it apart from what differs (`run_prompt(shared=…)`; the assistant places it behind the instructions) and runs its first call alone (`shared_first`). In the gap analysis of the demo (26 policies, 261 000 characters) every call carries 59 000 tokens: the first writes them ($0.18), each later one reads 55 000 from the cache and costs about $0.045 — against $0.17 when the documents went in the message.
- Usage is recorded in five numbers — the input whole, the part read from the cache, the part written to it, the output, the reasoning — and priced part by part (`assistant/usage.py`, `cost_of`). Before 2026-11-11 every input token was priced at the plain input price: a chat turn, which resends its instructions at each of its steps, was recorded at up to twice its cost.
- The estimate prices input as written to the cache, and the gap analysis as one write and many reads.

**Rate limits.** The provider counts tokens per minute (on 2026-11-10 four gap-analysis calls at a time, 59 000 tokens each, met Azure's limit within two minutes and failed the run). The assistant answers a provider's rate limit as a 429 with the wait the provider names — also when it arrives inside a stream that had begun — and a call made for a job step waits it out, up to fifteen minutes, instead of failing its step (`assistant/gateway.py`). A call a person waits for is retried briefly, as before.

**A report of the demo, measured 2026-11-11** on a copy of the database with the pipeline as it now stands, every act's obligations cut to its first fifteen (165 of 1 220): 7 min 44 s and $1.42 — citations $0.24, applicability $0.29, gap analysis $0.69 for 13 calls, action plan $0.16, summary $0.04. All 154 quotes were found in their documents; the plan closed all 98 open findings in three calls. In full that is about 82 gap-analysis calls: roughly $5 and 20–25 minutes, against $16.04 and 48 minutes for the 2 120 findings of the report of 2026-11-10.

**Visibility.** The usage page shows cost per day, kind, model and user; a call's detail says how much of its input was read from the cache and written to it.

## 9. Course context

The platform is the LegalOps project of the VU KnF course *Finansų teisė ir finansų įstaigų veiklos atitikties valdymas* (FinTech master's, autumn 2026). The course's three assignments on its sample organisation map onto the product:

| Assignment | What it asks for | Where it is in the product |
|---|---|---|
| 1, first prompt | Classify an organisation: the market, the institutes of financial law, the licence or list entry required. | A chat conversation that files `financial_market` on the company and cites the corpus. |
| 1, second prompt | A role profile — for example the compliance officer — from the company's own documents. | A `CompanyRole`, whose context a thread adopts through `{ROLE_CONTEXT}`. |
| 2 | A compliance policy in eight parts, the missing level-2 policies and level-3 procedures; then positions, an organisational structure, the compliance process in steps, and a RACI matrix with exactly one accountable and at least one responsible role per step. | The work products `policy` and `governance` (section 3): generated, checked against those rules by code, edited and approved by a person, exported as PDF — the policy also as Word; the governance product has no Word export. |
| 3 | Likelihood and impact criteria (five levels, four dimensions each), a 5×5 matrix with bands and responses, at least five scenarios in a set sentence typed by ISO 31022 Annex A, and the legal risk register. | The work product `risks`: the score and the band are computed, the register exports in the lecture's nine columns as PDF and Excel. |

The gap report itself is the method of the course's lecture on monitoring: a finding states the condition and the criterion, the action plan answers "now what", and a person approves the scope before the costly part and signs the report off. A finding carries the lecture's four parts — condition, criterion, cause (written by the reviewer) and consequence (from the act's own sanction provisions) — and the company's own policies can be the criteria of a group of their own (section 3, "What a finding means"). The plan of a signed-off report lives on in the company's action register, where an action is closed only by a later signed-off report that finds its obligations met — the lecture's findings-and-actions register with its re-test (section 3, "Over time").

The sample organisation, **1009 LTD** (a simulated 40-person CASP, CC BY 4.0), comes with 26 policies (13 ISMS, 13 FinTech). F00 cites some MiCA articles wrongly, which is what the citation check is for.

Where the course material and the sources differ, the product follows the sources: the Bank of Lithuania's guidelines on the compliance function are recommendations ("turėtų") addressed to the institutions their paragraph 3 lists, so for a crypto-asset service provider they are assessed only when a person takes them into a report's scope, as good practice; raising concerns is ISO 37301 clause 8.3 (investigations are 8.4).

## 10. Decisions

- **Django instead of FastAPI.** The user's call, taken before the spec was pasted.
- **Chat first; pages for review and administration.** The chat's tools cover company work only.
- **The system drafts and checks; a person approves.** The scope of a report, an obligation of the register, a finding's override, a work product: each is approved by a named person and audited, and nothing is marked approved by the system. Scores, bands and ids are computed by code, never taken from a model.
- **Corpus-level obligations with human review.** Reports record how many of their findings rest on reviewed obligations.
- **Official machine sources (CELLAR, e-tar) instead of EUR-Lex and e-seimas,** which refuse unattended clients.
- **The faculty Bifrost gateway (`ai.knf.vu.lt`) is the only model provider.** Company documents are sent to it for indexing (embeddings) and in the report steps, and whatever the chat reads travels with the chat turns; everything else runs on this machine.

## 11. Security review (2026-09)

The pre-release audit of the Django API. Its regression tests: `django/compliance/tests/test_authz_matrix.py` and `test_security_review.py`. The ingress it also checked has been rewritten since: it now guards the Origin, sends a Content-Security-Policy and HSTS, sets `X-Real-IP` from the `X-Forwarded-For` it receives and serves the administrators' database tool at `/dbgate/` (deployment.md §5). None of that was part of this review.

**How it was checked.**
- **An authorization matrix read from `urlpatterns`.** Every route × method × caller: anonymous (no, garbage, expired or deactivated bearer), a plain user, another user, an admin, the internal door without its secret. A new route fails the suite until it has a row.
- **A body fuzz.** Every JSON write starts from a body that succeeds. One field at a time is then replaced by an object, a nested list, a lone surrogate, a surrogate key or a boolean; the fields fuzzed are the ones the view reads (recorded). Malformed JSON goes to every write. No answer may be a 5xx.
- **Audit coverage.** Every admin write, and every admin write on another user's rows, must leave an audit row naming the admin.

**Findings, all fixed.**

| Severity | Finding | Fix |
|---|---|---|
| Medium | An MCP server URL could be any http(s) URL. The assistant connects to it from inside the isolated network, so an admin (or a stolen admin token) could make it call django `:8000`, postgres or its own `/internal` door, with the error text coming back in `lastError`. The egress allowlist guards only the way out. | https on port 443 to a public DNS name: no IP literal in any spelling, no container or local name. Enabling or testing a server needs such a URL; the internal door leaves out rows saved before the rule. |
| Medium | The per-account login window was keyed on the typed email. `email__iexact` compares with Postgres `UPPER()`, which folds `ı` and `ſ` to I and S, so `admın@…` signs in as `admin@…` with a fresh window per spelling. | Keyed on the account the email resolves to. |
| Medium | `change-password` checked the current password without a limit: a stolen bearer could guess it, change it and lock the owner out. | The check counts in the account's login window; a wrong one is audited. |
| Low | A lone surrogate in any JSON string (`"\ud800"`) made psycopg raise: a 500 on every write route, login included. | Refused with NUL at parse time. |
| Low | `1e999` parsed as `inf` past the NaN/Infinity guard. | Non-finite numbers are refused. |
| Low | `appliesTo` holding a list or an object: a 500 on corpus acts and obligations. | Strings are checked first. |
| Low | Binary content named `.txt` / `.html` was stored and embedded as garbage, or failed with a misleading 400; UTF-16 text failed. | Sniffed: binary is "Unsupported file type", UTF-16 with a BOM is read, control characters are dropped. |
| Low | Concurrent uploads could each pass the quota check. | Counted again after the insert; the upload that tipped it is undone. |
| Low | Transport errors of the model client (`HTTPConnectionPool(host='legalops-assistant', port=3000) … /internal/llm/generate`) reached report, job and corpus error texts. | Logged; the error says the AI service could not be reached. |
| Low | The citation check called the model past the caller's daily budget. | The word overlap judges once the budget is spent. |
| Low | Unbounded or untyped fields: a new account's email (an object containing "@" passed) and name, obligation texts, corpus `domains`, citation references, prompt-test variables; `reembed` queued any JSON as a document id. | Typed and capped; `reembed` needs an existing act. |
| Low | Prompt test runs and failed MCP connection tests were not audited. | Audited. |
| Low | `GET /api/llm/models` was open to every user. | Admin-only, as api.md lists it. |
| Info | Session tokens were uuid4 (122 random bits). | 256 bits; older tokens resolve until they expire. |
| Info | Stored file names kept any extension (`<uuid>.<script>`). | Only a plain short extension is kept. |

**Checked and sound.**
- **Tenancy.** A user gets 404 on another user's company, credential, role, document, report, finding, thread, message, job and usage call, for every method. That holds for a foreign child under an own parent and for ids in bodies and queries. Admins see every company, document, report, job and usage call, never another user's thread.
- **`/internal/*`.** Django and the assistant demand the secret on their internal doors (constant time, fail closed), and the endpoint forwards only `/api/…` paths to them.
- **Corpus fetchers.** https on port 443, checked again on every redirect; which hosts are reachable is the egress allowlist's call. The URL is rebuilt from the checked host, TLS is verified and the body is capped. DNS rebinding cannot happen: the hosts are pinned by `extra_hosts`, and Docker 27 resolves no external name on an internal network.
- **The extraction child.** No secrets in its environment; address space and CPU capped (a 96 MB input under a 64 MB cap is an error, not a crash); a wall-clock timeout; DOCX inflation capped.
- **Sessions.** Logout-all, a password change and an admin reset end the other sessions; deactivation and the operator's `manage.py create_admin --reset` with a password end all; expired rows are purged on sight. Every login refusal costs one bcrypt check.
- **Errors, exports, GUI.** A crash answers the bare `SERVER_ERROR` envelope, with the traceback only in the log. Exports escape every text, fetch nothing and write no formulas. The GUI renders model markdown without raw HTML.
- **Secrets.** `runUpdateThisStack.sh` mints hex only — since the review also DbGate's pair, a hex password and the Base64 of `dbgate:<password>` — reads `.env` with grep and never sources it, and prints no secret; the first admin's password is typed and handed to `create_admin` by name (deployment.md §3). `.env` is outside every build context, and nothing logs a secret.

**Residual risks (the operator's).** The operator's list, with what to do about each, is the "Operator checklist (residual risks)" at the end of [operations.md](operations.md).
- **The client address.** The outer proxy loses it for the visitors who reach it through the hop in front of it — four requests in five and nearly all signed-in use in the endpoint's access log of 2026-11-09 to 2026-11-16: for them it sends `X-Forwarded-For: 172.16.0.1`, the hop's address, and the endpoint copies the `X-Forwarded-For` it receives into `X-Real-IP`, where Django reads the client address (operations.md, "Client address"). The audit log's IP column shows that one address for all of them, and the per-IP login limit is one window they share: 60 attempts a minute block sign-in for all of them. A client cannot choose its address by sending an `X-Forwarded-For` of its own: the outer proxy overwrites that header (tested on 2026-11-16). The per-account limit (10 attempts, then 10 minutes) holds.
- **Secrets on the host.** `.env` and `AI.txt` (a copy of the gateway key) are mode 600 now (checked 2026-09-28); they were world-readable (644) before. Rotate the gateway key if other local users could read them then, and delete `AI.txt`. The live `.env` still holds the `ADMIN_PASSWORD` the old update script wrote: delete the line, and change the first admin's password in the GUI if it was never changed.
- **The hosting's management plane is trusted.** `sistema-filebrowser` (no login of its own) and `sistema-dockge` (with the Docker socket) mount `/apps/aplikacijos` read-write: `.env`, uploads and the database files. Only the hosting's control proxies reach them, by source IP.
- **Dev mode is live.** `docker-compose.yml` runs the dev servers on bind-mounted sources, and the dev assistant has open egress on the external network; production mode (deployment.md §6) ends both. The endpoint now checks the Origin and sends a Content-Security-Policy (framing by the site itself only) and HSTS (deployment.md §5); the policy still allows inline scripts and styles and `eval`.
- **The admin database tool.** `/dbgate/` serves DbGate to every active administrator: the endpoint asks Django's gate, then signs the request in to DbGate itself. DbGate logs in to Postgres as the superuser, so an administrator — or a stolen administrator session — reads and changes every table there, the password and session hashes, the chat transcripts and the MCP servers' header values included, past the API's validation, its tenancy rule and the audit trail: neither opening the tool nor a statement run in it leaves an audit row. The container runs as root; it sits on the isolated network and is reached only through the endpoint. It was added after this review and was not part of it.
- **The Docker socket.** `legalops-worker` holds `/var/run/docker.sock`, which is root on the host. It has no network and runs one fixed `docker exec`, so only a compromise of that container or of its image (`docker:27-cli`, pulled by tag) reaches the socket.
- **The SNI allowlist** trusts the named hosts' fronts. A compromised container could domain-front through a CDN that routes on the inner Host header; only TLS interception closes that.
- **Admins read chat transcripts.** The usage log's call detail carries every chat turn's text (the documented AI audit), while threads stay personal. The user guide says so (its privacy section).
- **Prompt injection.** A chat acts with the user's bearer. An instruction planted in a document that an admin's chat reads could steer the company tools across all companies. The tools cannot reach users, the corpus, prompts or MCP settings.
- **Cost.** Document indexing (embeddings) is charged to the uploader and gated by the daily budget: once it is spent, the indexing job re-queues itself for 00:05 UTC instead of embedding. The upload quota bounds what one account holds at once: at the defaults about $65–100 for 2 GiB of plain text and at most about $160–195 (1000 files at the 4-million-character extraction cap). Deleting documents frees the quota, so repeated upload-and-delete spends up to the account's daily budget, no more (unlimited accounts — admins by default — are not held back). Provider error texts pass through to report and job errors.
- **Upload spool.** Django spools uploads over 5 MB to its 512 MB `/tmp` tmpfs; about ten concurrent maximum-size uploads fill it, as does one oversized body (the endpoint caps nothing), and uploads then fail until the spool drains.
